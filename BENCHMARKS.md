# Benchmarks

servery ships a reproducible benchmark suite built on
[pytest-benchmark](https://pytest-benchmark.readthedocs.io/). It measures **per-request
latency** for every transport (HTTP/1.1, TLS, HTTP/2 ALPN + h2c, HTTP/3, WSGI, CGI,
ASGI, reverse proxy) plus the internal hot paths (HPACK, the frame codec, listing
rendering, Range parsing, the response-head builder, cert generation).

The functional test suite is `unittest` (run with `python -m unittest`); pytest is used
**only** here, scoped to `benchmarks/` via `testpaths` so the two never collide.

## Running

```bash
# all benchmarks (default free-threaded 3.14t interpreter)
uv run --group bench pytest benchmarks/

# one file / one case
uv run --group bench pytest benchmarks/test_bench_http1.py
uv run --group bench pytest benchmarks/ -k wsgi

# save a reproducible artifact + autosave for later comparison
scripts/run_benchmarks.sh

# fail if any median regressed >20% vs the last saved run
scripts/run_benchmarks.sh --compare

# also run the HTTP/3 end-to-end case (needs a GIL build + aioquic; see below)
scripts/run_benchmarks.sh --http3
```

`run_benchmarks.sh` writes a timestamped JSON to `benchmarks/artifacts/` and an autosave
under `.benchmarks/` (both gitignored — they embed per-round timings and the hostname).
It also records a concurrent-load JSON with throughput, p50/p95/p99 latency, errors,
and sampled peak/delta RSS. The RSS scope is the in-process server plus its client
workers, so use deltas and before/after comparisons rather than treating it as an
isolated server-process measurement. Client workers drain bodies in bounded 64 KiB
chunks so a large-file sample does not allocate one whole response per worker and
swamp the server-side memory signal.
`listing_scale.py` separately records render time, page bytes, and Python peak
allocation at 1,000, 10,000, and 100,000 real directory entries; file creation is
outside each timed sample.

The weekly/manual `Performance trends` GitHub Actions workflow runs both tiers,
including HTTP/3, and retains the JSON artifacts for 30 days. These results are trend
evidence rather than a strict pull-request gate: hosted-runner noise makes small
percentage thresholds misleading. Deterministic bounded-memory, race, and overload
recovery behavior remains enforced by the functional suite on every CI build.

## Comparing external servers

The in-process suite answers “which servery path changed?” It cannot honestly answer
“how does servery compare with a production edge or application server?” The separate
Docker harness compares byte-identical workloads in three cohorts:

- static files: servery, nginx, and Caddy;
- one shared WSGI app: servery and Gunicorn `gthread`;
- one shared ASGI app: servery and Uvicorn.

Opt-in framework cohorts run the same pinned Starlette or FastAPI app under
servery and Uvicorn. Starlette 1.3.1 runs in the standard CPython 3.15 image.
FastAPI 0.139.0 is an explicit `--include-fastapi` image layer and currently uses
CPython 3.14 because Pydantic Core 2.46.4 has no cp315 wheel.
Native Uvicorn is a separate `--include-uvicorn-native` Python 3.14 cohort. The
portable adapter explicitly selects asyncio/h11; the native adapter explicitly
selects uvloop/httptools, so Uvicorn's `auto` detection cannot silently merge the
two labels.

```bash
# list the static and dynamic scenarios
uv run python scripts/compare_servers.py --list

# default: concurrency 1 + 64, three trials, isolated server/client CPUs
uv run python scripts/compare_servers.py \
  --json benchmarks/artifacts/external-comparison.json
```

The harness validates status, length, and body hash before timing; rotates server order;
records image IDs, interpreter/GIL state, tail latency, client CPU, errors, and cgroup
memory; reports median, min/max, and median absolute deviation; marks rows where client
CPU reaches 90%; and rejects any run containing timed errors. WSGI, ASGI, and static
results are reported separately rather than collapsed into a misleading overall ranking.
For high-rate or high-connection work, `--max-latency-samples` bounds retained
latencies without changing exact counts, `--persistent-warmup` keeps established
connections across the measurement boundary, and `--connection-ramp` separates
steady-state clients from simultaneous admission bursts. The evidence records
the selected controls, status histogram, and status-versus-transport error split.
Capability-scoped scenarios can also require exact response headers. The
`static-digest-miss-64k` cohort validates the RFC 9530 `Repr-Digest` before timing
production, a prebuilt baseline, and the selector prototype with explicit digest
workers and zero retained entries.
The `static-listing-100` and `static-listing-1000` cohorts build fixed-mtime
directories, resolve expected generated bytes once under UTC, then require exact
body hash, CSP, referrer, and `Vary` parity. One- and four-worker selector
adapters expose the active listing budget; both retain the production entry,
pagination, and detail limits.
Opt-in WSGI/ASGI streaming cases emit byte-identical 64 KiB and 1 MiB bodies as
16 chunks/events. The current fixture is mounted into candidate and baseline
containers so a prebuilt old image cannot silently benchmark different app code.
Opt-in `asgi-churn-1k` serves the same minimal ASGI body with one request per
connection and a 32-client cap. It protects connection/protocol lifecycle changes
that a keep-alive-only ASGI benchmark would not see.
Opt-in `asgi-headers-32` adds 30 stable custom fields to loadgen's `Host` and
`Connection` fields. It protects request-parser cost scaling and validates the
same response bytes; it is not intended as a universal browser/proxy request mix.
Opt-in `wsgi-body-64k` and `asgi-body-64k` send one deterministic 64 KiB POST
body, require the mounted app to consume it completely, and validate the same
1 KiB response. The harness's candidate-only `--servery-request-body-timeout`
control supports same-image enabled/disabled deadline comparisons.
The opt-in ASGI slow-reader case emits 64 MiB as 1,024 distinct allocations to
four clients throttled to 16 KiB per millisecond. Treat its cgroup peak and errors
as the result: its completion rate is deliberately controlled by the client.
Opt-in `asgi-starlette-json`, `asgi-starlette-stream-64k`,
`asgi-fastapi-json`, and `asgi-fastapi-validation` add real framework routing,
request wrappers, JSON, 16-event streaming/disconnect tasks, and exact `422`
validation. Scenario app specs and fixture hashes are recorded; external
servery/Uvicorn results use the same within-trial paired-ratio summary as frozen
candidate controls. With both framework and native flags enabled on Python
3.14, the same scenarios run under explicitly portable and explicitly native
Uvicorn in one image; installed optional packages never change an adapter by
auto-detection.
Two explicit static architecture adapters are also available for research:
`servery-selector-spike` is the minimal ceiling test, while
`servery-selector-prototype` adds shared parsing, pipeline ownership, admission,
deadlines, counters, and graceful drain. Neither is a shipped backend or a fair
feature-parity replacement for production servery.
Filesystem-offload variants are likewise explicit research controls. They use a
bounded worker/queue budget and immediate `503` saturation; the default selector
prototype keeps warm local acquisition inline because pooled dispatch materially
regresses that workload.
Opt-in `static-range-64k` and `static-not-modified` cases exercise shared 206/304
selection. Scenario-defined request fields are validated before wire assembly;
the client accepts protocol-defined bodyless 1xx/204/304 framing while continuing
to reject unframed body-bearing responses.
The opt-in `static-index-1k` case adds contained directory/index lookup before
the same validated 1 KiB response; it is not a generated-listing benchmark.
Capability-scoped `static-download-1k` and `static-spa-1k` cases validate the
exact disposition or explicitly enabled fallback before timing only matching
production/selector adapters. Scenario adapter allowlists prevent unlike
nginx/Caddy defaults from entering these semantic comparisons.
Capability-scoped `static-gzip-cache-64k` and `static-gzip-miss-64k` cases
validate deterministic gzip bytes plus coding/Vary headers. Adapter names expose
retained-cache and selector worker/queue policy; cached and zero-retention
results are never collapsed.
Capability-scoped `static-access-log-1k` pairs logged and unlogged current and
frozen production with selector `drop` and async `wait` overflow policies. The
selector adapters expose queue, batch-size, and batch-window policy in their
commands. Warmup records are drained and truncated before timing; timed records
are counted after quiescence and reported as delivery percentage. Cgroup memory
is captured before the out-of-band audit helper runs.

For a local candidate A/B, prebuild the old source under a distinct image tag and
pass `--servery-baseline-image TAG`. The harness creates matching static, WSGI,
and ASGI baseline entries for whichever servery cohorts are selected. Candidate
and baseline rotate within each trial, and the report includes median per-trial
RPS/p99 ratios plus ratio MAD and range. Use these paired ratios rather than
dividing independently sampled aggregate medians.

See [External server comparison benchmarks](docs/design/server-comparison-benchmarks.md)
for the fairness contract, exact workload matrix, publication procedure, limitations,
and multi-worker scale run. The related
[Performance and production-gap research roadmap](docs/design/performance-gap-research-roadmap.md)
turns the measured static/concurrency gaps into staged profiling, prototype, and
decision work. The
[Production capability gap](docs/design/production-capability-gap.md) ranks the
operational features that throughput alone cannot measure.

## HTTP/3 note

`aioquic` (the QUIC stack) has no free-threaded build, so it can't be imported on the
default 3.14t interpreter. HTTP/3 is therefore covered in two layers:

- `test_http3_build_response_*` — the servery-owned request→response path (path safety,
  file/listing read, header assembly). Pure stdlib, **always runs**.
- `test_http3_end_to_end` — a real QUIC/H3 round-trip via aioquic over one persistent
  connection. `importorskip`-gated; run it on a GIL build:

  ```bash
  uv run --python 3.13 --group bench --extra http3 pytest benchmarks/test_bench_http3.py -k end_to_end
  ```

## Reference numbers

Single keep-alive connection, single thread (so this is **latency**, not peak throughput),
on a free-threaded CPython 3.14t build (GIL off). Your absolute numbers will differ; the
*ratios* are the durable signal.

### Transports — per request

| Transport | Client | Median | ops/s |
|---|---|---:|---:|
| WSGI (bare app) | http.client | ~47 µs | ~19.5k |
| ASGI (bare app) | http.client | ~49 µs | ~19.4k |
| HTTP/1.1, 1 KiB file | http.client | ~89 µs | ~10.4k |
| HTTP/2 cleartext (h2c) | httpx | ~288 µs | ~3.1k |
| HTTP/1.1 over TLS, 1 KiB | httpx | ~274 µs | ~3.2k |
| HTTP/2 ALPN (over TLS) | httpx | ~331 µs | ~2.8k |
| Reverse proxy (→ upstream) | http.client | ~386 µs | ~2.5k |
| HTTP/3 e2e (QUIC, on 3.13) | aioquic | ~380 µs | ~2.4k |
| HTTP/1.1, 8 MiB (sendfile) | http.client | ~1.69 ms | ~570 (≈4.9 GB/s) |
| CGI (fork + exec) | http.client | ~11.9 ms | ~84 |

### Internal hot paths — per call

| Path | Median | ops/s |
|---|---:|---:|
| `_http1.build_head` | ~0.84 µs | ~1.17M |
| frame serialize (DATA) | ~0.99 µs | ~1.0M |
| `ranges.parse` | ~1.10 µs | ~894k |
| frame parse (DATA) | ~1.54 µs | ~638k |
| HPACK encode (request) | ~3.46 µs | ~286k |
| HPACK decode (request) | ~4.23 µs | ~235k |
| `http3.build_response` (file) | ~17.4 µs | ~57k |
| `listing.render` (52 entries) | ~354 µs | ~2.8k |
| `_certgen.generate` (RSA-2048) | ~0.5–0.9 s | ~1–2 |

## Reading the results — what the numbers say

- **WSGI and ASGI are the fastest** request paths (~19k ops/s) — no filesystem, tiny
  body — and ASGI's asyncio loop matches the threaded WSGI path on a single connection.
- **The TLS/HTTP-2/HTTP-3 rows are driven by httpx/aioquic**, which add real client-side
  cost; compare those rows *to each other*, not to the `http.client`-driven plain rows.
  Among them: TLS h1 ≈ h2c > h2-ALPN ≈ h3 — TLS framing on a single stream is cheaper
  than h2/h3's multiplexing machinery when you're not actually multiplexing.
- **CGI is ~250× slower than WSGI** — it forks and execs a fresh interpreter per request.
  That's inherent to CGI; the benchmark shows the cost rather than hiding it. Use WSGI/ASGI
  for anything hot.
- **Large-file serving is sendfile-bound** (~4.9 GB/s on loopback), not CPU-bound.
- **HPACK decode is the slowest HTTP/2 hot path** (~4.2 µs/request) — the place to look
  first if h2 header throughput ever matters.
- **`listing.render` dominates directory serving** (~354 µs for 52 entries). Profiling
  shows the time is spread across necessary work — per-row HTML building, one `stat` and
  one `localtime` per entry, URL-quoting and HTML-escaping each field — with no redundant
  pass to remove. It's already tuned (an `lru_cache` on extension parsing, hand-rolled
  time formatting to avoid `strftime`/`datetime` allocation). Cost scales with entry count
  and is capped at 100k entries per request (the scan DoS guard).
- **`--tls-self-signed` costs ~0.5–0.9 s once at startup** — pure-Python RSA-2048 key
  generation. This is the price of zero runtime dependencies (there's no OpenSSL keygen
  binding to call). It's one-time per process and never persisted; a faster EC dev key
  would need a pure-Python ECDSA implementation (possible future work). For a long-running
  server it's noise; for rapid restart-driven dev loops it's noticeable.

## Throughput (concurrent) vs latency (this suite)

pytest-benchmark measures single-call latency. For **concurrent throughput** (req/s under
load, MB/s, tail latency) on the HTTP/1.1 file path, use the load tools:

```bash
python scripts/bench.py --requests 5000 --concurrency 16        # table
python scripts/bench.py --requests 5000 --concurrency 16 \
  --json benchmarks/artifacts/load-local.json                   # retained evidence
python -m servery /some/dir -p 8000 -q                          # one shell
python scripts/loadgen.py http://127.0.0.1:8000/file -c 64 -d 5 # another shell
```
